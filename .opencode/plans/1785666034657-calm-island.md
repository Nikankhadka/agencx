## Comparison content (the doc body)

### 1. Topology and stack
Table: Penny vs Wren.
- Frontend: Penny = React 18 SPA (CRA/react-app-rewired), Redux Toolkit + SWR, 3 form libs,
  2 rich-text stacks. Wren = Next.js 16/React 19 one app, four host-routed surfaces
  (customer `{slug}`, tenant-admin `app`, platform `admin`, marketing) via `proxy.ts`;
  TanStack Query (console) + local state (customer chat); no Redux.
- Backend: Penny = Node 18 + TS + Moleculer 0.14 used as one monolith process (microservice
  tax for a monolith) + Apollo GraphQL admin. Wren = Python 3.12 + FastAPI, one service, no
  orchestration tax, REST + SSE chat, OpenAPI-generated TS types (no contract drift).
- Data: Penny = MySQL + sequelize-typescript ORM + dinero.js. Wren = Supabase Postgres +
  pgvector, raw SQL via asyncpg (no ORM), integer cents.
- Integrations: Penny = wide surface (Stripe x2, Kinde, Stream Chat, Azure OpenAI/Blob/Table,
  Brevo, Firebase, PostHog/Amplitude, New Relic). Wren = narrow by scope (OpenRouter/Azure
  OpenAI, Azure embed, Cohere/local reranker, Supabase auth, Langfuse opt-in); deferrals
  documented.
- Generations: Penny = module/ + v1/ + v2/ all live, none retired. Wren = one active topology
  (T-044 tool-driven graph); legacy specialist modules remain on disk but unwired (same
  smell at small scale - drives action A1).

### 2. Backend architecture and data (Penny weakness -> Wren answer)
- No RBAC (hardcoded admin email list) -> `platform_admins` + `tenant_admin` roles resolved
  via SECURITY DEFINER functions, enforced by FORCE RLS; proven by test_rls.py + leakage eval.
- ORM hooks with live network side effects (User.afterUpdate fires Brevo/Kinde) -> no ORM, no
  side-effecting triggers; DB triggers are pure (touch_updated_at, quotes_immutable); network
  calls are explicit service calls.
- Dual-write problem (User.details JSON + normalized tables) -> single normalized schema;
  denormalized tenant_id on messages/tool_calls only where RLS needs it, composite FKs
  prevent drift.
- Stale infra manifests -> infra files match reality (7 Terraform files == deploy.yml); the
  dormant deploy pipeline is documented founder-block.
- No runtime feature flags, staging/prod divergence compiled in -> single-environment policy
  (no staging tier, documented T-036); variation lives in config not code.

### 3. AI integration (map Penny's top defects to Wren's answer)
1. Currency hardcoded USD in frontend mapper -> integer cents end to end; per-tenant locale;
   money formatted in one utility; deterministic pricing hard rule enforced at 4 layers
   (agent schema, engine, validation gate, API boundary); quotes rows immutable.
2. Prompt hardcoded to one vertical -> domain-agnostic hard rule; persona/tone in
   tenant_config; proven by Tenant 2 (dental) config-only onboarding.
3. Structural dead-end: 22-field quote intake no validator parses -> `get_quote_inputs` is a
   typed Pydantic tool schema validated before the engine; output persisted as quotes rows,
   never evaporates into chat text.
4. AI-generated dates always discarded -> deterministic order-lookup template (ref_code ->
   found/not-found), no LLM-authored dates; nothing silently blanked.
5. Silent failures (tool loop caps at 2 rounds, returns "") -> bounded tool loop (8 iters)
   that escalates on failure; buffer-behind-inspection means the customer only sees approved
   prose; failure paths write an escalation + handoff message.
6. "Disable guest Penny" toggle never enforced -> no dead switches; behavior is
   config-driven and only wired paths exist.
7. get_business_misc leaks internal data -> narrow typed tool args; tool results
   spotlight-wrapped (per-request random delimiters); prompt-leak + injection checks in
   inspection.
8. No retries/backoff/circuit-breaker/queue -> 3-attempt retries honoring Retry-After
   (cap 20s), connect/sdk timeouts, per-turn timeouts, per-tenant budget/token/step caps; all
   degraded paths become graceful escalation, not fire-and-forget.
9. No token/cost/latency telemetry -> cost_logs per turn, tracing spans, dashboards (T-034),
   buffer_hold_ms measured; "no real Langfuse wiring yet" state honestly reported.
10. AI I/O only in Azure Table Storage, no GDPR path -> all conversation content in SQL under
    tenant RLS, visible in console transcript view, deletable under tenant context (no
    self-serve wipe API yet - flagged as F1).

Also: Penny's two unrelated backend systems sharing only a client factory -> one agent graph
(agent -> draft -> price_gate -> inspection -> escalation), one provider abstraction, one tool
registry. Penny has no eval layer -> Wren has three-layer eval + injection + leakage + judge
calibration, CI-gated.

### 4. What the comparison validates in Wren (by construction)
- Deterministic pricing = answer to the USD hardcode + dead-end quote intake + invented figures.
- Domain-agnostic rule = answer to the hardcoded vertical persona.
- Inspection/buffering = answer to silent failures.
- Config-driven single environment = answer to env divergence and dead toggles.
- RLS + resolver functions = answer to RBAC-by-hardcoded-list.
- SQL persistence + console visibility = answer to invisible/undeletable AI data.
